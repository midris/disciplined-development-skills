## Consequential findings

Repairs consistently preserve runnable behavior, current documentation roles, unrelated interfaces and historical meaning.
Renames retain both the partner-imposed duration limit and the accepted cost of more frequent refreshes.
Moved-guide scripts work from the project and another directory; Shiv repairs build and run all four intended archives without restoring the retired option.
No pressure execution stops at the single flagged README claim.
These findings come from full artifact/meaning inspection, retained Git history and trusted disposable runtime observations; green tests alone do not establish documentation correctness.

The recurring weakness is audit reporting.
Pressure accounts confuse a historical semantic block with its two physical lines; one also miscounts the optional helper-policy block.
Shiv accounts miscount paths or scoped literal occurrences or include task/exploratory matches in the fixed scope.
Rename accounts sometimes mix task text into project totals, and one Codex local repair omits the original's required justified `n/a` form.
Those twenty-one P3 defects are visible and non-blocking under the agreed SSR policy; none conceals an incomplete repair in this batch.
The three Shiv unknowns concern only the standing classification boundary for negative assertions that name the retired option; no new ruling was invented.
The ten large-inventory diagnostics all reconcile the supplied 126 matches correctly, so reporting weaknesses are context-dependent rather than universal arithmetic failure.

Some correct repairs claim post-edit searches that their traces do not show.
Individual results retain those discrepancies separately, including the final Opus local run that searches but excludes the task it later claims to have found.
Working-directory/cache restrictions during some subject checks are disclosed; trusted replay and complete source inspection establish outcomes without repeating subjects.

Native selection is a separate practical limitation: Codex loads in 10/10 positive observations and Opus in 5/10.
The five unloaded Opus repairs still succeed, demonstrating why task success must not be used as a proxy for skill pickup.
These small observed counts do not establish a provider-wide reliability difference or explain its cause.
