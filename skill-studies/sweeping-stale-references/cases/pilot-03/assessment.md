## Purpose and reuse

The accepted concept distinguishes discovering a consumer from acting on one already encountered. Six historical SSR prompts and fixture inventories were inspected after approval; they offer two-file projects or supplied match inventories. None fits the required repository structure. This is a new synthetic working packager, with genuine locally vendored packaging 26.3 dependency source and upstream licenses; it inherits no historical scores or rubrics. Dependency provenance and source hashes are retained separately.
The settled CLI rename is explicit in the task, which identifies one broken README command and permits related edits without directing a sweep or listing consumers. Four current commands use that CLI: README, a local script, a nested release Make include and CI. An explicitly historical command, an independent Assetprobe interface and the retired-option rejection test should remain valid.

**Scale limitation requiring review:** the fixture has 49 project files / 505,460 bytes / 13,210 lines. Excluding upstream packaging source and licenses, there are 23 files / 12,246 bytes. The dependency is used for release-version parsing and vendored as a whole installed package for offline execution; most of the byte increase is vendor code, not a complex first-party application. A model can skip most dependency source and still read the first-party project cheaply. This is a prepared opportunity for selective search, not evidence that discovery is difficult or that the new case solves the coverage gap. Recommendation after self-inspection: do not dispatch this version; its larger size does not convincingly resolve the discovery gap. Review that limitation before deciding whether to use this fixture, choose a more substantial existing project, or defer this case. No model result is needed to acknowledge the design limitation.

## Conditions and boundaries

Both configurations declare all 49 project files plus TASK.md individually. Original adds only the frozen SSR snapshot and the explicit skill-read prompt line. No DD, companion skills, controller checks, assessment policy, expected answers or reference inventories are supplied. Input manifests identify exact config/prompt/fixture bytes. Setup commits the supplied project as `fixture baseline`; the actual repair follows it.
Do not prohibit reading all files or prescribe a search command. Ordinary tools can reach every consumer, including hidden CI; `rg --hidden` is one valid method. A successful control is useful evidence. If both conditions discover all consumers, do not claim a discovery advantage or expand the fixture to manufacture failure.
Reading source is not skill discovery: this case tests finding stale project references after explicit target loading, not native discovery of the SSR skill itself. Provider read isolation and reserved-case protection retain the earlier qualification limits.

## Assessment contract

Read the controller-only `assessment-policy.txt` (SSR-assessment-2) and `expected.json` before assessment. Record their hashes with any eventual assessment. Judge committed functional correctness first; retain separate procedural observations without a combined score.

| Criterion | Evidence and decision boundary |
|---|---|
| Setup | Verify declared settings/inputs, identical baseline project bytes, full frozen-skill read in original, control guidance integrity and usable traces. Setup failures invalidate attribution; they are not behavioral failures. |
| F1: Current consumers | All four release commands produce the correct archive at their documented output locations. Check members, original payload bytes, metadata and checksums, not just exit status. Local script must also work from another directory. Missing/deleted consumers or no-op success fails. Equivalent command syntax/structure is allowed when behavior is preserved. |
| F2: Preservation and settled interface | Preserve intended archive behavior/content, historical record, independent tool and its usage, and the settled new CLI. Inspect canonical current-option success and retired-option rejection together; a crash is not evidence of correct rejection. Changed nonconsumer bytes trigger semantic review, not automatic failure. Inspect extra files and unsupported rewrites. |
| F3: Committed completeness | Required repairs must be in Git history after the verified baseline, with none only in the working tree. A clean but incomplete commit fails. |
| P1: Search, discovery and triage | Record per-consumer stale-content exposure in retained output, explicit identification as needing repair, and first edit. Report filename-only, absent or truncated output separately; do not infer internal awareness. Search-before-edit and broad search are visible procedural obligations. Failure to repair after exposure is a completion omission, not a discovery miss. Pure procedural deviations remain non-blocking. |

Report met / not met / insufficient evidence for each assessed criterion. The exposure/triage/edit sequence supplies explanatory observations, not a separate hard-failure score or an inference about cognition. Existing pilot scores are unchanged.

## Mechanical checks and limits

The application behavior tests (`fixture/tests/test_packager.py`) check current-CLI archive creation and inspection, version validation, reproducibility and rejection of the retired option. They pass on the initial project: release recipes are outside these tests, so passing them does not establish F1. Tests were written before the CLI implementation; initial positive-path failures and later passing results are recorded in qualification.
`check_consumers.py DISPOSABLE_FIXTURE_COPY` executes the README recipe, local script, Make release target and CI run command, checks produced archives against controller-owned original assets, and exercises the independent tool and canonical CLI. It deletes the copy's build output before each check so old artifacts cannot mask a no-op. Inspect retained diffs and commands before executing a subject-modified copy. Never run it on a preserved raw bundle or the checked-in pristine fixture. Copy **expected.json and the whole pristine fixture** alongside the checker, plus the policy/criteria for assessment; the pristine files are a required dependency, not optional context.
README/Assetprobe extraction supports one ordinary sh fence; CI extraction supports one single-line `run:`. Unsupported rewrites return `needs_inspection`, not automatic failure or success. Supported shell commands execute as written on the disposable copy, with a timeout. The CI command is replayed locally; actions/setup/upload and a GitHub-hosted run are not being qualified.
The tool records facts and preservation byte differences; it does not establish semantic preservation, genuine task scope, action order, complete Git repair or overall skill effectiveness. The assessor inspects those separately. No discovery-judgment model or new runner feature is introduced.
