# SSR comprehensive rewrite comparison proposal

Status: completed owner-approved 34-call scope; see the [assessment](comprehensive-comparison-02-assessment.md). The protocol owns current decisions; this document preserves the executed design.
All 90 subject calls are spent, including the 34 calls specified here.
The original and existing comprehensive rewrite are the only selected conditions; this is comparative effectiveness and invocation testing, not a new no-skill contribution study.
The [preparation](invocation-pressure-preparation.md) owns the case designs and the [qualification](native-discovery-qualification.md) owns native-runtime evidence and its limits.

## Scope and allocation

| Stratum | Cases | Repetitions per condition | Calls |
|---|---|---:|---:|
| Explicitly loaded ordinary behavior | discovery-shiv, moved-guide, semantic-delivery, initiating-change, local-change | 2 | 20 |
| Explicitly loaded pressure | pressure-repair | 2 | 4 |
| Native positive invocation | invocation-change, invocation-review | 2 | 8 |
| Native non-use sanity check | invocation-unrelated | 1 | 2 |
| Total | Original and candidate in each row | | 34 |

Two repetitions retain the earlier comparison's modest variability check; the obviously unrelated sanity task gets one per condition because it supports a narrow claim.
Large-sweep-account remains an optional reporting diagnostic and is not repeated here; its baseline already isolates accounting, which is not the selected new question.
No controls, retries, replacements, evaluator calls or authoring calls are allocated.
Approval raises the combined subject ceiling from 56 to 90 for this batch only.
Selected runtime: Codex 0.156.0, gpt-5.6-sol, low effort, workspace-write, 900-second per-attempt timeout; pin the executable and final runner revision at freeze.
Time guideline: 180 active minutes (25 freeze/preflight, 65 model wait, 65 retention/assessment, 25 review/reporting); actual time is reported, not treated as additional call authority.

## Fixed order

Execute sequentially in the listed case order: discovery-shiv, moved-guide, semantic-delivery, initiating-change, local-change, pressure-repair, invocation-change, invocation-review.
For each case run original repetition 1, candidate repetition 1, candidate repetition 2, original repetition 2.
Finish with invocation-unrelated original then candidate, one attempt each.
This produces 34 slots; the schedule is counterbalanced within repeated cases, not randomized or blinded.
Preserve and verify each complete bundle before the next dispatch.
Inspect the first native-invocation session's actual catalog, skill path and capture before continuing native cases.
Stop for preservation failure, changed runtime identity, suspected contamination, missing native context or setup error; no automatic replacement follows.

## Acceptance and reporting

Apply frozen case criteria and policy meanings; positive invocation D1 is separate from task repair and cannot be rescued by functional success.
Sanity-check functional outcome is `not measured` and excluded from functional denominators.
Keep ordinary, pressure, positive invocation and sanity observations separate; never pool historical observations into these counts.
Compare pressure against the contemporaneous ordinary semantic-delivery case descriptively; the small suite cannot establish a causal pressure effect or population reliability.
Include all valid setups regardless of outcome; retain invalid/unknown/unattempted slots and charges explicitly.
A candidate functional regression or missed/late/incomplete invocation requires explanation before recommending adoption.
Tied outcomes do not show improved behavior; independently report any simplification benefit.
No numerical adoption threshold substitutes for owner judgment.

## Before dispatch

Before dispatch, materialize and byte-check all conditions, verify the candidate against the comprehensive worktree, freeze manifests/configurations/cards/policies and commit invocation authority.
Run collection readiness and installed-policy preflight for the pinned CLI, including the login-shell check and Shiv fixture compatibility.
Retain catalogs on actual production sessions; scripted qualification alone cannot establish model selection.
The Claude documentation cross-check informs a possible later provider comparison; it adds no Claude calls to this proposal.
