# Writing explicit rationale — focused baseline proposal

The owner selected [writing-explicit-rationale](../../skills/writing-explicit-rationale/SKILL.md) as the next study. This proposal covers four cases on Codex and Claude. The first question is whether the shipped skill helps a future maintainer recover a consequential decision from the edited artifact and leaves a routine edit free of unnecessary explanation. The second is whether each provider recognizes those situations on its own.

The [WER protocol](../../skill-studies/writing-explicit-rationale/protocol.md) owns current status, coverage, spending and decisions.

Read the full diff in context and ask what a future maintainer would actually do differently. For native runs, record timely skill loading separately. An unnecessary load on the rename and an unwanted edit are distinct observations.

### Reader-first output check

For each provider, give a fresh reviewer only the complete final project artifacts for each output under opaque labels. Keep task messages, review conversations, commit messages, submitted summaries, source facts, criteria, other scores and condition labels outside first-pass access. Before revealing them, capture the reviewer’s written account per output: What decisions can you recover? Where? Why were they made? What consequence or revisit condition, if any, can you infer? Record “unclear” where the tree is silent. Include the routine edit without hinting that a reason should exist.

Then release the original project, task and source facts, full diff, delivered response, replay evidence and frozen criteria. Compare the recorded reading with the actual decision, flagging missing, misleading or invented implications. Accept equivalent wording and an empty rationale for a self-evident edit. Check task behavior independently. Retain both passes and verify evidence access order before reconciling with the active assessment. A correct guess unsupported by the file earns no placement credit.

## Proposed run sequence

1. **Freeze and qualify offline.** Prepare neutral prompts, four small Git fixtures, expected facts, replay commands and rubric under the current study formats. Pin the shipped skill (SHA-256 `97eb06c649c194e8819b4dff68b808eda4ec7c948a6ead518da247daf31d6cfe`). Requalify installed CLI versions and permission boundaries. Proposed settings follow the previous study: Codex gpt-5.6-sol low, Claude Opus 5.5 low, workspace-write, 900 seconds. Keep the controller’s instructions, other skills and prior outputs out of the subject context.
2. **Application checkpoint — 16 subjects.** Run each case once per provider with the full skill explicitly loaded and once in a fresh no-WER control. Match all other inputs and alternate arm order. Check full delivery before work, inspect each final artifact and run the applicable behavior checks. Pause for diagnosis on an invalid setup, a changed policy, an incomplete skill-guided task, or a material invented rationale. A control failure is evidence about the comparison.
3. **Native discovery — eight subjects if the checkpoint holds.** Repeat the same four ordinary tasks once per provider with the skill available through its native catalog. Check catalog exposure and the ordered trace for full loading before the relevant edit. Expected use is yes for the deferral, quota change and repeated review, no for the routine rename. Keep artifact scores even when selection differs.
4. **Review and decide.** At the decision boundary, use two fresh read-only Opus-medium output reviews, one packet per subject provider, covering all its completed conditions and all four cases. Use the staged reader-first check above. Report disagreements and who reviewed each provider. Use subject traces for discovery. If both arms do good work, record that the screen found no incremental benefit. If a material failure appears, reproduce it in the smallest affected cell before proposing wording changes.

**Proposed ceiling:** 24 fresh subject calls, two evaluator calls, zero authoring calls and zero retries. Allow an estimated 120–200 active minutes for preparation, qualification, collection, assessment and review. One run per cell can expose a failure or justify a targeted repeat. It cannot rank providers reliably or establish a discovery rate. A repeat or broader comparison needs its own allocation. The owner has selected the skill and requested this plan. Model dispatch awaits approval and frozen inputs.
