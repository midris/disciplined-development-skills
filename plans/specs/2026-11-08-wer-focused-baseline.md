# Writing explicit rationale — focused baseline proposal

The owner selected [writing-explicit-rationale](../../skills/writing-explicit-rationale/SKILL.md) as the next study. This proposal covers four cases on Codex and Claude. The first question is whether the shipped skill helps a future maintainer recover a consequential decision from the edited artifact and leaves a routine edit free of unnecessary explanation. The second is whether each provider recognizes those situations on its own.

The [WER protocol](../../skill-studies/writing-explicit-rationale/protocol.md) owns current status, coverage, spending and decisions.

### Reader-first output check

For the three positive cases, use a fresh Opus-medium reader for each output whose decision-site changes could convey a reason. The controller records the eligibility reason for every output before seeing reader scores. Skip a first reading only when the unchanged site demonstrably lacks the required explanation; include ambiguous changes, new files, changed code that might convey intent, and partial repairs. Inspect the routine rename directly against its original diff. This measures recoverability for the read outputs only. Report skipped, missing and invalid readings separately.

Use an ordinary Claude read-only runner config with zero declared fixtures. Compose its prompt from the [neutral question](../../skill-studies/writing-explicit-rationale/cases/reader-question.txt) followed by the exact UTF-8 payload bytes. The runner still offers read tools. Accept the reading only if the launch and init records establish the read-only policy, fresh session with persistence disabled, expected catalog and no target exposure, the initial workspace has only its runner-created Git boundary, the captured prompt matches its expected bytes and the complete raw trace shows zero tool calls. Retain an unusable reading as such. Qualify this path first with one separately budgeted reader smoke on a constructed project.

Build each payload from the verified final project as sorted relative paths mapped to complete file contents. Exclude Git internals and verified study inputs (task, mounted skill and review attachment) by declared identity. Preserve new project files. A changed attachment, unreadable file, symlink, non-UTF-8 data or context overflow requires explicit resolution or an unavailable reading. Keep the project-to-subject mapping controller-only. Record the SHA-256 of the exact serialized payload, composed prompt and final reader answer plus the retained bundle inventory identity. These identify what was judged and when.

After sealing the eligible first readings, use up to two read-only reviewers, one per subject provider. The [reconciliation instructions](../../skill-studies/writing-explicit-rationale/cases/reconciliation-question.txt), packet index and per-output evidence include the recorded reading identities. Verify first-read completion precedes reconciliation start. Reviewers record their own judgments before any comparison with the active assessor. Use the runner's capture, retention and evaluator ledger for provenance and charges. Check for existing trace inspection helpers before writing any provider-specific logic.

## Proposed run sequence

1. **Freeze and qualify offline.** Prepare neutral prompts, four small Git fixtures, expected facts, replay commands and rubric under the current study formats. Mount the review attachment only at its declared supplemental path. Native subjects receive ordinary WER availability without DD or other routing companions; record the actual catalog and any deviation. Pin the shipped skill (SHA-256 `97eb06c649c194e8819b4dff68b808eda4ec7c948a6ead518da247daf31d6cfe`). Requalify installed CLI versions and permission boundaries. Proposed settings follow the previous study: Codex gpt-5.6-sol low, Claude Opus 5.5 low, workspace-write, 900 seconds. Keep the controller’s instructions, other skills and prior outputs out of the subject context.
2. **Application checkpoint — 16 subjects.** Run each case once per provider with the full skill explicitly loaded and once in a fresh no-WER control. Match all other inputs and alternate arm order. Check full delivery before work, inspect each final artifact and run the applicable behavior checks. Pause for diagnosis on an invalid setup, a changed policy, an incomplete skill-guided task, or a material invented rationale. A control failure is evidence about the comparison.
3. **Native discovery — eight subjects if the checkpoint holds.** Repeat the same four ordinary tasks once per provider with the skill available through its native catalog. Verify catalog exposure and apply each case card’s native-selection deadline to the ordered trace. Expected use is yes for the deferral, quota change and repeated review, no for the routine rename. Keep artifact scores even when selection differs.
4. **Review and decide.** At the decision boundary, run the isolated first readings above, then one read-only Opus-medium reconciliation per provider covering its completed conditions and cases. Report disagreements and who reviewed each provider. Use subject traces for discovery. If both arms do good work, record that the screen found no incremental benefit. If a material failure appears, reproduce it in the smallest affected cell before proposing wording changes.

**Proposed ceiling:** 24 fresh subject calls, up to 21 evaluator calls (one qualification smoke, at most 18 isolated positive-case readings and two reconciliations), zero authoring calls and zero retries. Separate readings are proposed because seeing another solution discloses the rationale. Direct diff inspection suffices for the routine rename. This bounded exception to grouped review awaits owner approval. Allow an estimated 160–260 active minutes for preparation, qualification, collection, assessment and review. One run per cell can expose a failure or justify a targeted repeat. It cannot rank providers reliably or establish a discovery rate. A repeat or broader comparison needs its own allocation. The owner has selected the skill and requested this plan. Model dispatch awaits approval and frozen inputs.
