- Identity claim: State that the worker is a dispatched development subagent, not the orchestrator; it must load and follow `disciplined-development`, obey its dispatch scope, and dispatch no further subagents. Support from `dispatching-development-subagents` (“When you dispatch,” “Red Flags”) and `disciplined-development` Principle 4.

- Hook claim: State that `review_nudge.py` is an advisory, exit-zero `PostToolUse` hook triggered only after a landed Git commit. It emits one accumulated response containing Gate 3 verification and any applicable T1/T2 cadence nudges. Support from the hook module documentation and `main()`.

- Gate claim: Distinguish Gate 3 from review/checkpoint/PR gates. The subagent owns verification of its committed work, but Gate 5, periodic adversarial review, checkpoint logging, and PR opening belong to the orchestrator. On a T1/T2 nudge, the subagent must report the gate as due and stop without reviewing, gathering findings, running `dd-log`, or opening a PR. Support from `GATE_AUDIENCE`, `disciplined-development` Gates 3 and 5, and Principles 4 and 8.

- Counter claim: Identify T1 as the branch’s `edits` counter reaching `review_tiers.regular.commit_edit_floor`—default 30. Identify T2 as commits since a usable checkpoint reaching `review_tiers.cold_read_escalation.nudge_threshold`—default 3—or, when the checkpoint is absent or invalid, commits since fork base. If repository, branch, fork-base, or trunk resolution fails, the applicable cadence segment is omitted. Support from `review_nudge.py` constants, configuration helpers, and cadence branches.

- Verification claim: Require the post-hook response to report the relevant running-system evidence—UI screenshot/DOM snapshot, live API response, actual CLI invocation, or another task-appropriate exercise—or explicitly state why the change is not exercisable. Passing tests alone must not be presented as sufficient verification. Support from `VERIFY_TEXT` and `disciplined-development` Gate 3.

- Dispatch-scope claim: Require the dispatch to name in-scope files and change shape, governing files, locked constraints, and the out-of-scope rule. Require the report to include `Changes beyond dispatched scope: none` or enumerate each extra change with rationale. Any extra change must be small, safe, obvious, separately committed, and disclosed; risky, large, uncertain, design-level, deletion, or overwrite work must only be surfaced. Support from `dispatching-development-subagents`.

- Commit-verification claim: State that the orchestrator must inspect every returned commit with `git show --stat`, then its diff, reconcile it against the scope contract, and decide out-of-scope changes on merit. Neither the subagent’s report nor passing tests establish scope compliance. Support from `dispatching-development-subagents` “Verify — orchestrator, non-negotiable.”

- Workflow-ownership claim: Map scope contracting, out-of-scope handling, report disclosure, and per-commit diff verification to `dispatching-development-subagents`; map plan-task execution and task-level spec/quality review to `superpowers:subagent-driven-development`; and map the Iron Law, five gates, cadence, whole-branch review, smoke pass, and PR boundary to the `disciplined-development` orchestrator.

- Expected post-hook response: Require the subagent to state the landed commit, provide Gate 3 evidence or a non-exercisability reason, identify each fired T1/T2 condition with its observed count and threshold, say that the corresponding orchestrator gate is due, disclose scope status, and stop. It must not claim to have completed orchestrator-owned review, checkpoint, or PR work.
