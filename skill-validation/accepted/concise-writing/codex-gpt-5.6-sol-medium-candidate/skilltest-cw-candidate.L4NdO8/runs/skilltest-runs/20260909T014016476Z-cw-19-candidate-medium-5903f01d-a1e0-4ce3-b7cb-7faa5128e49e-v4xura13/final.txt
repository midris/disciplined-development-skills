## Orders schema cutover

### Preflight and readiness

1. Run `./bin/schema-cutover preflight --plan orders-v3 --json`.
2. Attach the JSON output, including the pre-cutover snapshot ID, to change ticket `CHG-4821`.
3. Confirm that, during the same uninterrupted 15-minute window:

   - Database replica lag remains at most 2 seconds.
   - The dual-write mismatch rate remains below 0.1%.

If preflight fails or either metric breaches its limit before promotion, stop. Post `BLOCKED` with a link to `CHG-4821` in `#schema-cutover` and tag the database incident commander.

### Promotion

After the readiness window passes:

1. Post the `CHG-4821` link in `#schema-cutover`.
2. Wait for the database incident commander to reply `GO`.
3. Only then run `./bin/schema-cutover promote --plan orders-v3`.

Never add `--force`; it bypasses the readiness and `GO` checks and can expose partially backfilled rows.

### Recovery boundary

In-place rollback is permitted only until the application accepts its first write containing an `orders-v3`-only field. That write is irreversible because the old schema cannot represent it.

After that boundary:

- Do not run `./bin/schema-cutover rollback --plan orders-v3`.
- Only the database incident commander—not the release engineer—may decide whether to continue forward or restore the pre-cutover snapshot recorded in `CHG-4821`.
