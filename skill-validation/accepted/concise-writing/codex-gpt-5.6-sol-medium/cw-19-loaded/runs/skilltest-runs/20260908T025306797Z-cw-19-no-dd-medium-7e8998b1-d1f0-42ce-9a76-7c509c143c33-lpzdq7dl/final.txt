## Orders schema cutover

### Preflight and readiness

1. Run `./bin/schema-cutover preflight --plan orders-v3 --json`.
2. Attach the JSON output, including the pre-cutover snapshot ID, to change ticket `CHG-4821`.
3. Promote only after both conditions remain true together for the same uninterrupted 15-minute window:
   - Database replica lag is at most 2 seconds.
   - Dual-write mismatch rate is below 0.1%.

If preflight fails, replica lag exceeds 2 seconds, or the mismatch rate reaches 0.1% or higher before promotion:

1. Stop.
2. Post `BLOCKED` with a link to `CHG-4821` in `#schema-cutover`.
3. Tag the database incident commander.

### Promotion

After the readiness window passes:

1. Post the `CHG-4821` link in `#schema-cutover`.
2. Wait for the database incident commander to reply `GO`.
3. Only then run `./bin/schema-cutover promote --plan orders-v3`.

Never run the promotion command before the `GO` reply or add `--force`. The `--force` option bypasses the readiness and `GO` checks and can expose partially backfilled rows.

### Recovery boundary

In-place rollback is permitted only until the application accepts its first write containing an `orders-v3`-only field. That write is the irreversible in-place rollback boundary because the old schema cannot represent it.

After that boundary:

- Do not run `./bin/schema-cutover rollback --plan orders-v3`.
- Only the database incident commander—not the release engineer—may decide whether to continue forward or restore the pre-cutover snapshot recorded in `CHG-4821`.
