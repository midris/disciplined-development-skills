# Membership Roster Import Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Safely replace the active membership roster from a validated CSV containing at most two million members, with atomic visibility and one actionable rejection report.

**Architecture:** Stream the upload so memory usage does not grow with the file size, while staging validated rows in temporary storage that enforces unique `member_id` values. After the complete upload passes validation, pass the staged roster to the application’s persistence boundary for one atomic replacement; every rejection path must leave the active roster untouched.

**Tech Stack:** Python standard-library CSV parsing and temporary storage; the project’s existing Python test framework and roster persistence mechanism, to be confirmed from the two named files during implementation.

**Spec:** `context/import-brief.md`

## Global Constraints

- Each non-header row has `member_id` and `email`.
- `member_id` is the immutable external identity and must be unique within the file and active roster.
- The replacement becomes visible only after the entire file succeeds; no partial roster may be visible.
- Uploads may be absent, empty, malformed, or as large as two million rows.
- Two million rows is the supported maximum; reject larger uploads without changing the active roster.
- The operator needs one actionable error report when an import is rejected.
- Do not introduce an email-format policy beyond requiring the specified `email` field unless the existing contract already defines one.
- Preserve the established public API, storage abstractions, test runner, and error conventions found in the named files; the concrete names below describe the required behavior and should be mapped onto those conventions rather than creating duplicate APIs.
